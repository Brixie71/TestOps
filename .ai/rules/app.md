# App

## Workflow discipline: rules index, docs search, narrowest tests
Before creating or editing files, read .ai/rules/index.md when this directory exists. Search Laravel ecosystem documentation (Boost search-docs) before relying on ecosystem APIs, behavior, or version-specific syntax. Run the narrowest test set covering each change (php artisan test --compact with a file path or --filter) and rerun after every change. Create documentation files only when explicitly requested. Unresolved revision items are not approved features or requirements: the Revision 2 SQL command item stays unclarified until the user states otherwise, so design nothing around it.

## User account lifecycle (implemented, Stage 3B)
- `App\Actions\DeactivateUserAction` and `App\Actions\ReactivateUserAction` own user lifecycle transactions; controllers stay thin. Deactivation soft-deletes the user (no new `account_status` value), revokes user-bound OAuth credentials only through `App\Services\Auth\RevokesUserCredentials`, purges the target user's database sessions on the configured session connection/table, and audits `user.deactivated` + `oauth.credentials.revoked` (aggregate counts only) through `AuditLogger` inside the same transaction. Reactivation restores the account, preserves `account_status`, never restores revoked credentials or old sessions.
- `App\Services\Users\LifecycleConnectionGuard::assertConsistentConnections()` must run before any lifecycle transaction: lifecycle, session (`SESSION_CONNECTION` null→default), and Passport (`PASSPORT_CONNECTION` null→default) connections must resolve to the same connection; fail closed otherwise.
- `App\Services\Users\UserLifecycleAuthorizer` reuses `PermissionChecker` — the only lifecycle permission code is `users.deactivate`. SYSTEM_ADMIN needs the seeded `users.deactivate` permission (`UserManagementPermissionSeeder`); project-scoped roles never grant it; users cannot act on themselves; non-Super-Admin actors cannot target SUPER_ADMIN/SYSTEM_ADMIN roles; the last active Super Admin is protected.
- The canonical SUPER_ADMIN system role row (`code = SUPER_ADMIN`, `scope = system`) is the serialization root for every operation that changes the number of active Super Admin accounts: `DeactivateUserAction` (reduces), `ReactivateUserAction` (increases), and `PermanentlyDeleteUserAction` all acquire `lockForUpdate()` on that row inside their transaction and fail closed when the row is missing; the target (including soft-deleted rows) and the actor are then reloaded from the database under the lock, and authorization, target eligibility, and lifecycle-state checks are re-evaluated against that state — never rely on a count taken before the transaction. Reactivation applies no last-active-Super-Admin restriction (it can only increase the active count). Future lifecycle operations (system-role changes, bulk deactivation) must acquire the same row lock before changing that state. (SQLite compiles the lock to a no-op; it takes effect on PostgreSQL/MySQL.)
- `EnsureActiveAccount` (alias `active.account`) runs after `auth` on authenticated web routes only — never on login/logout/invitation routes — logging out soft-deleted or non-`active` accounts with session invalidation + CSRF token regeneration.
- `App\Actions\PermanentlyDeleteUserAction` owns permanent deletion (§7.3): Super Admin only (`UserLifecycleAuthorizer::assertCanPermanentlyDelete`), never self-service, deactivated accounts only, and confirmed with the acting admin's own password plus a reason. It reuses `RevokesUserCredentials`, purges sessions, deletes every `user_email_addresses` row (releasing current and previous addresses for reuse, §9.3), then force-deletes; audit history survives because `audit_logs` has no `users` foreign key. `App\Services\Users\UserDeletionDependencyInspector` lists restrictive blockers (currently `projects.owner_id`) and the foreign key remains the final guard.
- `DeactivateUserAction` also performs the §7.1 email cleanup inside the same transaction: every `pending` `user_email_addresses` row is released (deleted) and outstanding `PURPOSE_EMAIL_CHANGE` tokens are invalidated; the current verified email is preserved and reactivation never revives the cancelled request (§7.2).
- `App\Services\Notifications\AccountSecurityNotificationService` sends the mandatory §14.2 security notifications after the owning transaction commits: account deactivation, account restoration, system-role changes, and self-service password changes. Sends are synchronous, use the immutable `NotificationDeliveryRecorder` (`account_deactivated`, `account_reactivated`, `system_role_changed`, `password_changed`), carry no internal administrative details, and can never roll back the account operation because every outcome — including mail failure — is recorded without throwing.

## Email address management and verification security (implemented, Stage 6)
- `App\Actions\{Request,Complete,Cancel}EmailChangeAction` own the self-service email-change flow (§9): current-password confirmation, a `pending` reservation in `user_email_addresses`, single-use token through `EmailVerificationService::PURPOSE_EMAIL_CHANGE`, atomic completion that flips the old address to `previous`, and cancellation (self or admin) that releases the pending address. Admin cancellation needs `users.email.manage` plus a recorded reason and notifies the current verified address.
- `EmailVerificationService` enforces §10.3-§10.8 on issuance: 60-second resend cooldown, 5-per-rolling-hour account limit, configurable per-IP hourly limit (`EmailVerificationLimitSettings`, `accounts.email_verification_ip_hourly_limit`), and a 30-minute lockout once the request-level counter reaches 10. Limits gate replacement issuance only; a refused request never invalidates the outstanding token or releases the pending reservation.
- `email_verification_requests` carries `issued_at`, `requested_ip`, and the token-level `failed_attempts`; `email_verification_attempt_counters` holds the request-level counter per user and purpose (reset only by a successful verification or an elapsed lockout). Rejected attempts are recorded by the controllers after the consuming transaction rolls back.
- Guests confirm changes through `email-change/confirm/{token}` (GET previews without consuming, POST consumes); the profile owns `profile.email.update` and `profile.email.cancel`. Do not add further verification-email senders without wiring the same issuance limits.
- The profile shows the account holder's own recent notification deliveries (§15.6): type, timestamp, effective status (latest manual retry when present), and `user_message` for failures only. Never expose `failure_code`, `failure_message`, retry internals, or any retry control to ordinary users.
- Manual delivery retries (§15.4–§15.5) are limited to types with a reconstructible resend path: invitation link/direct setup (credential rotation) and the security notifications `account_deactivated`, `account_reactivated`, `system_role_changed` (role names from the `user.role_changed` audit snapshot), `password_changed`, plus `email_change_cancelled`. Verification, email-change verification, and forced-password-reset deliveries stay non-retryable because their single-use tokens are never stored; users request fresh emails through the normal workflows.

## Notification preferences (implemented, 14.3-14.4)
- `user_notification_preferences` stores one row per account with `project_activity_enabled` and `system_announcements_enabled`, both defaulting to enabled; a missing row means both optional categories are on. `User::notificationPreference` exposes the relationship.
- `PATCH profile/notifications` (`profile.notifications.update`, behind `auth` + `active.account`) updates only the signed-in account's two optional flags; an unchecked category is stored as disabled. Security and account activity notifications are mandatory and have no stored flag, so they must never be gated on a preference.
- Optional-category senders must resolve the current preference immediately before delivery through `App\Services\Notifications\NotificationPreferenceChecker` and record a suppressed `NotificationDelivery` row (`NotificationDeliveryRecorder::recordSuppressed`, status `suppressed`, reason `preference_disabled`) instead of sending. Suppressed rows appear in the admin history with their reason and are never retryable. No optional-category sender is wired yet.

## User profile editing (implemented)
- `App\Actions\UpdateUserProfileAction` owns both self-service and administrative profile editing (§3.1, §6.3, §6.5). It writes only `name`, `contact_number`, `job_title`, and `department` (trimmed, blank → null), never email, password, role, or account status; unchanged submissions write and audit nothing; every change audits `user.profile_updated` with before/after snapshots.
- Self editing is always allowed through `PATCH profile` (`profile.update`). Editing another account requires `users.profile.manage` (seeded to SYSTEM_ADMIN by `UserManagementPermissionSeeder`), is rejected for the actor's own account, respects `UserLifecycleAuthorizer::isProtectedTarget()`, and targets deactivated accounts with a 404 because the administrative route uses implicit binding.
- `App\Actions\ChangeOwnPasswordAction` owns the self-service password change (§6.5, §11.4) exposed as `PATCH profile/password` (`profile.password.update`): the account holder confirms their current password, `PasswordPolicy` validates the new password, the current session survives while every other database session row for the account is deleted, OAuth tokens are untouched, `user.password.changed` is audited without password material, and the `password_changed` §14.2 notice is sent after commit.

## Audit log access and exports (implemented, §12.4)
- `App\Http\Controllers\Settings\AuditLogController` serves the filtered audit page and both exports under `audit.view`. CSV and PDF exports reuse `validatedFilters()` + `filteredQuery()`, so every file matches the on-screen filters (§12.5), and each export writes `audit.exported` with the active filters plus `format=csv|pdf`. CSV streams in 500-row chunks; PDF renders `settings.audit-logs-pdf` through `barryvdh/laravel-dompdf` in landscape A4.
