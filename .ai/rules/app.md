# App

## Workflow discipline: rules index, docs search, narrowest tests
Before creating or editing files, read .ai/rules/index.md when this directory exists. Search Laravel ecosystem documentation (Boost search-docs) before relying on ecosystem APIs, behavior, or version-specific syntax. Run the narrowest test set covering each change (php artisan test --compact with a file path or --filter) and rerun after every change. Create documentation files only when explicitly requested. Unresolved revision items are not approved features or requirements: the Revision 2 SQL command item stays unclarified until the user states otherwise, so design nothing around it.

## User account lifecycle (implemented, Stage 3B)
- `App\Actions\DeactivateUserAction` and `App\Actions\ReactivateUserAction` own user lifecycle transactions; controllers stay thin. Deactivation soft-deletes the user (no new `account_status` value), revokes user-bound OAuth credentials only through `App\Services\Auth\RevokesUserCredentials`, purges the target user's database sessions on the configured session connection/table, and audits `user.deactivated` + `oauth.credentials.revoked` (aggregate counts only) through `AuditLogger` inside the same transaction. Reactivation restores the account, preserves `account_status`, never restores revoked credentials or old sessions.
- `App\Services\Users\LifecycleConnectionGuard::assertConsistentConnections()` must run before any lifecycle transaction: lifecycle, session (`SESSION_CONNECTION` null→default), and Passport (`PASSPORT_CONNECTION` null→default) connections must resolve to the same connection; fail closed otherwise.
- `App\Services\Users\UserLifecycleAuthorizer` reuses `PermissionChecker` — the only lifecycle permission code is `users.deactivate`. SYSTEM_ADMIN needs the seeded `users.deactivate` permission (`UserManagementPermissionSeeder`); project-scoped roles never grant it; users cannot act on themselves; non-Super-Admin actors cannot target SUPER_ADMIN/SYSTEM_ADMIN roles; the last active Super Admin is protected.
- The canonical SUPER_ADMIN system role row (`code = SUPER_ADMIN`, `scope = system`) is the serialization root for every operation that changes the number of active Super Admin accounts: both `DeactivateUserAction` (reduces) and `ReactivateUserAction` (increases) acquire `lockForUpdate()` on that row inside their transaction and fail closed when the row is missing; the target (including soft-deleted rows) and the actor are then reloaded from the database under the lock, and authorization, target eligibility, and lifecycle-state checks are re-evaluated against that state — never rely on a count taken before the transaction. Reactivation applies no last-active-Super-Admin restriction (it can only increase the active count). Future lifecycle operations (system-role changes, permanent deletion, bulk deactivation) must acquire the same row lock before changing that state. (SQLite compiles the lock to a no-op; it takes effect on PostgreSQL/MySQL.)
- `EnsureActiveAccount` (alias `active.account`) runs after `auth` on authenticated web routes only — never on login/logout/invitation routes — logging out soft-deleted or non-`active` accounts with session invalidation + CSRF token regeneration.
- Deferred (do not implement silently): pending email-change cancellation (no email-change module exists — integrate when it lands), deactivation notifications, permanent deletion.
